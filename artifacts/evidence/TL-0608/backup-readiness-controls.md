# Backup readiness keyboard and scaling evidence

TRACE now invalidates the previous backup readiness result when the size
or recovery confirmation changes. A different saved handover context
clears both inputs. The signed-in operator can review the new prerequisites
without carrying forward a prior recipient's declaration.

On 27 November 2026 the native x64 Windows 11 host ran Targeted with locked
restore. Quick passed 1,446 .NET tests. Five selected WPF cases passed,
including the named Extended maintenance keyboard journey, controlled
Toggle Keys and sign-off. The full run took 193.470 s without skips.
The application and test inputs were based on
`2be6a208b1e26cb7d73b3e1bda58a554d582fe75` plus the source at
`b1f34ee516e3c8ace141caf576b67fd172f1d8e6`. The latter adds a separate
explicit-volume observation, run independently after Targeted.

The current Backup readiness test used a 660 × 520 DIP window, 2× layout
transform, isolated high-contrast resources and a long German button
label at 22 points. The size, recovery confirmation and action followed
keyboard order. The action fitted the scroll viewport. Missing consent
returned focus to the confirmation, and a read-only result focused the
polite live region. Editing scope cleared the old result. Sealed handover
cleared and hid the inputs.

A separate ActiveMachine selection ran `WindowsFileHistoryTests` against
the explicitly scoped local development volume on the host. The runner
set `THIRDLIFE_FILE_HISTORY_TEST_VOLUME` to that drive root. The partition
probe confirmed a disk distinct from the Windows disk. Two tests passed
in 39 ms, including positive capacity and repeat opaque binding and
negative system-volume, subfolder and invalid-route checks. It wrote no
backup data. Live backup, native restore, physical DPI and audible
screen-reader observations remain open.
